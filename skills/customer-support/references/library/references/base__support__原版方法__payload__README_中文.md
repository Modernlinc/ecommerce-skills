# 客服离线回复与交接

将一个获准客服事项转成能审阅的英文内部答复、中文依据、时间线与待人工接手材料。此为实用版V1本地候选（0.4.0-practical-v1-candidate-01，新用途待独立检查），需在能读写指定本地文件的现有Codex环境中显式加载；未全局安装，不连接收件箱、不发送消息、不查询或修改订单。用途为获准低敏问题摘要和公开/自有非敏感政策的新任务；合成材料只是一种验证材料。真实客户原话、工单/订单及摘录改写/脱敏件须读前另找使用者确认。

## 准备这一个事项

先提供类型、来源、敏感性和用途元信息，按[业务正文读取前](base__support__原版方法__payload__references__input-output-contract.md#业务正文读取前)确认可读范围；不先上传真实客户正文。准入通过后，给一个组织/事项的问题摘要或获准合成消息、适用商品/FAQ、输出位置及已给定的角色职责。摘要无需客户原话或真实订单；不把操作者假设写成客户已提出。缺信息写unknown，缺会话/订单编号留空，生成的本地编号要标明。政策保留来源、版本、适用范围和截至；摘要日期不当客户事件日期。

完整字段见[输入输出契约](base__support__原版方法__payload__references__input-output-contract.md)。不要求先购买Gorgias/respond.io、安装插件或登录厂商后台；厂商教育仅为来源，非运行依赖。

## 委托一次

保留整个support-offline-reply-handoff文件夹的11件结构，把以下位置替换为当前真实路径：

> 请使用这里的客服 Skill，帮我处理指定材料里的这件事，给我一份可审核的英文回复和需要内部接着处理的事项。仅作本地草稿，完整结果保存到我指定的位置。

把本目录METHOD.md、这件事的获准材料和输出位置明确给出即可，不必先决定专业分组或正确处理路线；Skill会读取必需资源并说明取舍。先看当轮完整英文草稿及关键理由/待办，完整JSON供回查，不是发送许可。

若读不到候选，先检查文件完整性、位置和权限；不以旧对话答案代替加载。业务事实只来自这次输入，来源研究不是本次订单证据。

## 接着处理同一事项

每轮先说明新材料类型/来源/敏感性，准入通过后给出这件事新增或更正的事实/摘要目标及其来源，说明与原事项的关联即可；不必重新填全部字段。只在本次获准且可读的材料范围续接，不搜索客户目录。Skill会保留仍有效的信息和未决事项，更新受影响的当前回复与交接；旧输出不代替事实，客户明确改目标时按新目标处理。

每轮看完整的当轮草稿、变化与仍需内部处理的事项。完整JSON另存新输出，原首答保留；材料补齐不表示已退款、已改订单、已联系或已接手。

## 三处看懂结果

1. `internal_reply_draft`：可供人工审核的自然英文。看它是否真正回答有据部分、保留截至/条件/相对日期锚点，没有虚构当前订单、已转交或处理期限。不是可直接发送许可。
2. `chinese_explanation`、`time_line`、`intent`：逐项回到输入，区分事实、自述、推断、请求、未知与拟行动。平台规则参考只能解释规则，不能证明订单或个案资格。
3. `routing`、`human_handoff`、`safe_next_action`：看接手人需要判断的具体问题、证据与缺口。角色不可用/路径失败应写清最小内部下一步；无角色依据就请操作者指定，不编造联系方式。没有回执必须pending，不能把被@、被分配或被关闭当接手/解决。

输出总计14顶层键，human_handoff保留19键。五个permission_unknowns固定unknown，含义是本事项适用性/发送资格未核；已知退出仍必须记录。ready_to_send=false；无回执时accepted/receipt/resolution为空、resolved与external_handoff_executed为false。完整结构见契约。

## 何时停止、何时维护

无处理权限先停正文处理；对象混入、关联或证据不清时只停受影响部分。缺最新物流不阻止独立FAQ实答。明确要人不能用继续问答拦住；通用说明不能冒充个人适配或批准。真实查询、发送、退款、实际接手均超出本包。

发现资料确实需要维护才使用[四列知识反馈表](base__support__原版方法__payload__templates__knowledge-feedback.md)：问题/来源→错因→最小拟改→原问题复查。备注不是有效知识，不自动更新或逐单建档。
