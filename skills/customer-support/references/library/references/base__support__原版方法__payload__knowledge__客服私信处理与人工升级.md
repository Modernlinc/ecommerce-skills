# 客服私信处理与人工升级

实用版V1公司方法候选；不是reviewed终验结论。用途为获准低敏问题摘要与公开/自有非敏感政策的有据完整回复及待接手材料，不是客服系统。实际验证与独立QA见[VERSION](base__support__原版方法__payload__VERSION.json)及具名回执；本文件随候选自足携带，本轮未写Vault。

## 先实答，再交清楚的问题

按[中文入口](base__support__原版方法__payload__README_中文.md)先加载方法，再依[契约](base__support__原版方法__payload__references__input-output-contract.md#业务正文读取前)用元信息确认准入，之后才打开指定业务正文。允许新低敏摘要及公开/自有非敏感政策，合成只是一种输入；真实客户/订单及摘录改写脱敏件仍须读前另找使用者确认。摘要没有客户原话也可起草，描述者与假设不能变成客户证言或订单事实；不为一般FAQ索取真实客户正文。后续新材料同样先过门禁。通用商品/服务事实、个人适配/批准或当前订单状态、明确要人分别识别。适用FAQ能答的给实答；旧快照仅支持其截至时点，客户自述不是系统状态。客户明确要人时不要求先继续问答；可附简短事实，不拖延、劝退。保留客户条件、原消息日期/时区锚点，缺基准不借运行日补齐。

英文给客户需要的事实和限制；中文给依据、未知及拟动作。业务引用回到本次输入，内部评论/标签不混进对客段落。政策参考可以解释规则，但不证明订单、同意、账号或单条消息可发。

## 人工能接着做，而不是只看见一份摘要

[19键交接模板](base__support__原版方法__payload__templates__handoff-record.json)保留问题、客户条件、已知事实及截至、缺口、给定角色与具体下一内部动作。角色存在/可用、被分配/被@、实际接受、问题解决不是一个状态。无回执pending，不宣称正在核查或已转交；关闭标签不等于解决。角色不可用或路径失败时，让给定协调角色确认负责人和可达路径；无依据不指定真人、不捏造电话或SLA。不重复索取已有信息，不索取完整敏感标识。

商品/订单、商业条款、数据及经营后台等只能按输入确立的职责拟分流；规划中的公司领域不证明接口接通。Support负责整理服务事项和证据，Meta广告权限不授予WhatsApp访问。

## 反馈要改到有效知识才算落地

[知识反馈表](base__support__原版方法__payload__templates__knowledge-feedback.md)按需区分缺知识、错用/漏用、过宽分流、语气和权限。先查已有合格知识，再提最小修订与原问题复查；无增量可no_update_needed。内部备注/理想回复只是反馈，不证明知识已生效；本包不自动更新FAQ、Skill或厂商配置，权限缺失不能靠提示词修复。

## 当前事实、成熟度与停止

[平台规则参考](base__support__原版方法__payload__references__current-platform-policy.md)仅为2026-10-11核验的WhatsApp政策§1–3快照；不是完整政策或法律意见。五unknown指个案适用性未知，明确退出不能被抹去，ready_to_send始终false。无真实资料授权停止正文处理；发送、查询、退款、实际接手超出本包。

来源与公司设计分层见[来源映射](base__support__原版方法__payload__references__source-map.md)：G01/G02同案例，不是独立效果验证；G01原帧未核，G03日期不足只作研究参考；respond.io贡献协作状态边界，不证明本环境已联调。方法保持company_design/method_hypothesis，合成验证不等于real_project_validated。旧PWE/静态接收不覆盖本新版，正式独立结论须另以实际冻结报告为准。
