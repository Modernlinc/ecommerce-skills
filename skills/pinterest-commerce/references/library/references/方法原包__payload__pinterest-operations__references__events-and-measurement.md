# 事件与衡量：把业务事实、平台证据和算术分开

## 逐事件判断

先看业务完成了什么、发生时间和订单依据，再对照已证语义。P14说明观察到的Checkout/checkout对应完成交易，InitiateCheckout/initiate_checkout对应发起但未完成。这里仅解释输入日志标签，不是上传枚举表。不能仅看英文checkout就判错，也不能把“支付成功”设为覆盖所有交易方式的通用定义；若业务完成与结算时点不同，要求适用交易流程证据。明确未完成且未支付的购物车与完成交易语义不合。

逐行报告：原业务状态、原标签、渠道/关联ID、商品/金额/币种、发现、影响、下一证据。同订单browser/server记录可构成一组重复观察；不意味着Pinterest实际接收或去重。不同订单不共享事件身份；缺ID的记录无法稳定建立跨渠道关联，不能为了让计数好看补一个随机值。P15的详细跨渠道规则保留历史选段日期，P17补读了去重结果层；无新尾部正文不假装重新验证所有规则。

P14金额依据以商品价值口径核对，来源选段描述税/运费前商品总额与明确币种。按输入交易真值比较，不沿用catalog错币种或账户默认值，不把退款当负数购买事件。退款用于单独对账，本候选不提供发送方案。金额口径或业务状态不足时列unknown，不替商户制定税务/支付规则。

## 六层证据不能跳跃

1. 商业交易：订单/支付/取消/退款记录证明什么业务发生。
2. 采集观察：本地browser/server日志，只证记录存在。
3. 接收/处理：请求逐事件返回和错误，不能只看HTTP成功。
4. 测试诊断：Test Events警告和推荐字段情况，不等真实流量正确。
5. 去重：Event ID覆盖、duplicate removed与Events Overview对应对象/期间；相同ID只是候选条件。
6. 归因/经营：报表窗口、匹配、click/view、订单和退款。不从任何上一层直接推出归因或净利润。

同意/授权状态必须单列；不知道就保持真实数据传输HOLD。无需也不得请求用户密钥或身份资料完成离线诊断。

## 指标和差异

保存率=同窗同过滤保存数/展示数；站外点击率=同口径站外点击/展示。展示分母0为N/A；窗口/过滤器不合不计算，不能将点击、保存相加成人数或相乘成漏斗。Pin clicks仅原数；Pin click rate未知不算不排。paid-and-earned不能直接归给本期广告支出，保存后的传播不等新付费。

记录时间区、完整日期区间、内容对象、地区、来源/格式、是否含saved、实时状态、链接添加日。优化用的conversion window与评估的attribution window作用不同；都保留回溯时长和click/view类型。P16来自Leads页窗口段，不证明Sales账户具体可选窗口或默认值。

转化报表还需单独记录日期归集依据：所给报告按广告互动日期还是按转化发生日期归集，并保留原标签、该报告版本/说明及实际设置的证据定位。它与观察起止区间、时区、归因回溯窗口、导出时间分别记录，不互相代填。若使用本地标签report_date_basis，只作公司记录标签，不代表原生CSV列或API请求参数。依据未知或不同，停止依赖该可比性的比较、合并与差异解释，分别保留原数据及其他有证描述；依据相同也仍须满足已有同口径条件，不自动判定可比。不按历史SDK默认值补实际选择，不自行移动日期、换算或重归集记录。优先补证为该份报告的日期归集说明与实际选择证据；拿不到时保持受影响判断unknown，不要求连接真实账号。

订单对账先按时间/币种/商品金额与退款期间分层。独立列：报表自述归因购买/金额、给定订单已完成交易数/商品金额、已知退款后商品小计、未知成本与净利润。若可做本地窗口候选筛选，明确它不是平台真实归因：还缺身份/触点全量/配置/返回。报表金额÷同口径花费至多是报表原始比值，质量有问题时不能叫已验证回报，更不能用全店净额顶替归因净额。
